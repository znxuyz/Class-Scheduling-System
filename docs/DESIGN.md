# 國小排課系統設計

涵蓋**教師配課**與**教室排課**，並且要能吸收老師們各式各樣的個別需求
（「週三不要排我的課」「一天不要超過四節」），同時保證教室不重複使用、
老師不會同時出現在兩個班。

本文的每個設計決策都由 `prototype/` 下的可執行原型驗證過，實測數據附在
[§7 實測結果](#7-實測結果)。

---

## 1. 先認清國小的特性

國小排課和國高中差很多，設計從一開始就該吃進這些前提：

| 特性 | 對設計的影響 |
|---|---|
| **包班制**：導師教國語、數學、社會、綜合等大部分科目 | 一位導師的課集中在單一班級，天然不會自我衝堂；真正難排的是跑班的科任老師 |
| **班級有固定原班教室** | 大多數課不需要「分配教室」，教室衝突只發生在音樂/電腦/美勞/體育/自然等專科課 |
| **專科教室通常全校只有一間** | 這是最稀缺的資源，也是最常見的無解原因 |
| **低年級課少** | 每天不上第 7 節、週三下午不上課 → 班級層級的「不可排課時段」 |
| **綜合活動、生活課常排連堂** | 排課單位不全是單節，要支援長度 2 且不可跨午休的區塊 |
| **課綱規定各領域節數** | 「每班每科一週幾節」是輸入條件，不是可調整的變數 |

**推論**：不要照抄大學或高中排課系統的模型。把「原班教室」設成預設值、
只對專科課建立教室決策變數，問題規模會小一個量級。

## 2. 兩階段：配課 → 排課

```
基本資料 ──► 課綱節數 ──► 【配課】 ──► 可行性檢查 ──► 【排課】 ──► 人工微調 ──► 發布
 班級/教師     每班每科      指派老師       擋掉注定       自動求解      鎖定+局部
 教室/科目     一週幾節                    無解的配課                    重排
```

**這兩件事必須分開，但不能各做各的。**

- **配課**決定「誰教哪個班的哪一科」。這是人的決策——年段協調、專長、行政減
  課、資深老師的偏好，牽涉校內政治，不適合也不應該全自動。
- **排課**決定「哪一節、在哪間教室」。這是純組合最佳化，該全自動。

關鍵在於**配課的結果直接決定排課有沒有解**。若把電腦課配給一位老師教 12 個班
每班 3 節 = 36 節，而全校只有一間電腦教室（一週 35 個時段），這在配課完成的
瞬間就已經無解了。所以兩階段之間一定要插一道**可行性檢查**（§5）。

## 3. 資料模型

### 3.1 時間格線

```
Grid: days=5, periods=7  →  slot 0..34（0-based 整數）
      morning        = [1,2,3,4]     上午節次
      double_breaks  = [4]           第 4↔5 節之間是午休，連堂不可跨越
```

把時段壓成一個整數 `slot = (day-1)*periods + (period-1)`，所有衝突約束都變成
「同一個 slot 上的計數」，模型會乾淨很多。

### 3.2 實體

| 實體 | 關鍵欄位 | 說明 |
|---|---|---|
| `Subject` 科目 | `room_type`, `is_core` | `room_type=None` 代表在原班教室上 |
| `Room` 教室 | `type` | `homeroom` / `music` / `computer` / `pe` / `art` / `science` |
| `SchoolClass` 班級 | `grade`, `homeroom`, `blocked[]` | `blocked` = 該班不上課的時段 |
| `Teacher` 教師 | `max_per_week`, `max_per_day` | 硬性鐘點上限 |
| `Requirement` 配課 | `class_id, subject_id, periods, teacher_id, doubles` | **這就是配課階段的產物** |
| `Constraint` 需求 | `kind, params, hardness, weight` | 老師的各種要求（§4） |
| `Unit` 教學單元 | `length ∈ {1,2}`, `pinned_slot` | 排課的最小單位 |

### 3.3 為什麼要有 Unit 這一層

`Requirement`（501 班國語，一週 6 節，王老師）不能直接拿去排——要排的是那
**6 個獨立的時段**。展開成 Unit 之後：

- 連堂自然表達成 `length=2` 的單元，而不是「兩個必須相鄰」的耦合約束
- 人工鎖定（`pinned_slot`）落在單元上，粒度剛好
- 求解器只需要處理一種東西：把 N 個單元放進格線

範例學校 12 班 → 132 筆配課 → **328 個待排單元**。

## 4. 老師的需求怎麼表達 —— 這是整個系統最關鍵的設計

### 4.1 不要為每種需求開一個欄位

最容易犯的錯，是在 `teachers` 表上長出 `no_monday`、`max_per_day`、
`prefer_morning`… 每收到一個新需求就改一次 schema。國小老師的需求是**開放
集合**，明年一定會冒出你今年沒想到的。

改用**統一的約束表**：

```json
{ "kind": "TEACHER_DAY_OFF",
  "params": { "teacher": "S_EN1", "day": 3 },
  "hardness": "soft",
  "weight": 200 }
```

新增一種需求 = 新增一個 `kind` 與對應的建模函式，資料表結構不動。

### 4.2 硬約束 vs 軟約束 —— 必須分清楚

這是排課系統成敗的分水嶺。

**硬約束（Hard）：違反了課表就是錯的，不容妥協**

1. **班級不衝堂** — 一個班同一時間只能上一門課
2. **教師不衝堂** — 一個老師同一時間只能教一個班 ← *你問題中的需求*
3. **教室不衝堂** — 一間教室同一時間只能有一堂課 ← *你問題中的需求*
4. **節數守恆** — 每個 (班級, 科目) 剛好排滿課綱規定的節數
5. **班級不可排課時段** — 低年級週三下午不排課
6. **教室型態相容** — 音樂課只能排在音樂教室
7. **連堂完整性** — 必須在同一天相鄰節次，且不可跨午休
8. **教師鐘點硬上限** — 法定/校規的節數天花板

**軟約束（Soft）：盡量滿足，違反要付出代價**

| 需求 | 預設權重 | 說明 |
|---|---|---|
| 老師希望某天完全沒課 | 100 | *你問題中的「哪幾天不排」* |
| 老師希望避開特定時段 | 100 | 進修、兼課、行政會議 |
| 老師一天最多 N 節 | 40 | *你問題中的「一天不要超過幾節」* |
| 老師最多連續 N 節 | 20 | 不要連上五節喘不過氣 |
| 同科目一天最多 N 節 | 10 | 國語一天不超過 2 節、數學不超過 1 節 |
| 老師課表不要有零星空堂 | 5 | 跑班老師的痛點 |
| 某科避開某節 | 8 | 體育不排午餐後第 5 節 |
| 主科盡量排上午 | 2 | 國語數學排在學生精神好的時候 |

**權重的數量級要刻意拉開。** 老師「整天不排課」的承諾被打破，成本必須遠高於
一節課沒排在上午——否則求解器會為了湊十幾個小偏好，犧牲一個對老師而言重大
的承諾。

### 4.3 老師的需求該設成硬的還是軟的？

**強烈建議：除了法規與物理限制外，一律設成軟的，用權重表達重要性。**

理由：老師的需求彼此會打架。三位科任都說「週三不要排我的課」，而週三又必須
上課，這時系統若把它們當硬約束，只會吐出一句「無解」，教務主任完全不知道
該去找誰協調。

設成軟約束的話，系統會給出一份**違反最少**的課表，並明確報告：

```
狀態 OPTIMAL　懲罰 128
!  102 導師 一天最多 4 節（超出的節數）（成本 120）
!  體育避開第 5 節（成本 8）
```

主任看到這行，就知道要去找 102 導師談「這週有一天會到 7 節」。這比「無解」
有用一百倍。

實務上的做法是：**先全部設軟的跑一次**，看犧牲了什麼；真正不可退讓的（例如
老師週三下午固定在外校兼課，人根本不在）再改成硬的。原型中音樂老師週五下午
不可用就是硬的，因為那是物理事實。

## 5. 可行性檢查 —— 在求解之前就把話講清楚

求解器回報「INFEASIBLE」對使用者毫無幫助。但**絕大多數的無解，在配課完成的
瞬間就注定了**，而且用簡單的計數就能抓出來，還能明確指出是誰的問題。

排課前先跑這幾道檢查：

1. **參照完整性** — 配課指到不存在的班級/科目/教師
2. **班級容量** — 某班配課總節數 > 該班可用時段數
3. **教師週鐘點** — 配課總節數 > 週上限，或 > 扣掉不可用時段後的剩餘時段
4. **教師日上限的總量** — 配課節數 > 日上限 × 可上課天數
5. **專科教室容量** — 該類型教室的總需求節數 > 教室數 × 每週節數
6. **科目無人任教** — 有課綱節數但沒配到老師

實測輸出（把電腦課從每班 1 節改成 3 節）：

```
✗ 教師 電腦老師 配課 36 節，超過週上限 20 節
✗ 教師 電腦老師 配課 36 節，但一天最多 5 節 × 5 個可上課日 = 25 節
✗ computer 類型教室需求 36 節，但 1 間 × 35 節 = 35 節，容量不足
✗ 班級 5 年 1 班 配課 34 節，但一週只有 33 個可上課時段
```

每一行都直接指向要改什麼。這些是**必要條件**，通過不保證有解，但沒通過一定
無解——而且成本極低（純計數，毫秒級），值得在配課畫面上即時跑。

> 若通過了前置檢查求解器仍回報無解，代表是硬約束之間的交互作用。這時用
> CP-SAT 的 `AddAssumption` + `SufficientAssumptionsForInfeasibility()` 可以
> 反推出**哪一組硬約束互相矛盾**，回報給使用者。

## 6. 排課演算法

### 6.1 選 CP-SAT（Google OR-Tools）

排課是 NP-hard 的組合最佳化問題。三個主要選項：

| 方法 | 優點 | 缺點 |
|---|---|---|
| **CP-SAT** | 能證明最佳性、加新約束只需幾行、無解時能給出矛盾集 | 規模極大時可能爆記憶體 |
| 基因演算法 / 模擬退火 | 實作簡單、隨時可停 | 不保證滿足硬約束、調參玄學、無法證明無解 |
| 手刻回溯 + 啟發式 | 完全可控 | 加一種新需求就要改演算法本體 |

**國小規模用 CP-SAT 是壓倒性的正確選擇**——實測 48 班、1312 個單元，31.7 秒
求得**最佳解**（見 §7）。而且第 4.1 節那種「新需求 = 新 kind」的擴充性，只有
宣告式的約束求解器給得起。

基因演算法在排課領域被過度使用了。它在你能寫出精確約束模型的時候沒有優勢，
而排課的約束是可以精確寫出來的。

### 6.2 建模

**決策變數**

```
x[u, s, r] ∈ {0,1}   教學單元 u 從 slot s 開始、使用教室 r
```

把「時段」與「教室」**合併進同一個變數**是關鍵技巧。若拆成兩組變數（時段一組、
教室一組），教室衝突就變成兩個變數的乘積，得引入一堆 channeling 變數；合併之
後，教室衝突退化成單純的線性不等式。

長度 2 的連堂單元佔用 `s` 和 `s+1`。定義：

```
covers(u, s) = { x[u, s-offset, r] : offset ∈ [0, length), r ∈ 候選教室 }
             = 所有會讓單元 u 佔用到 slot s 的變數
```

**硬約束全部建立在 covers 上，各一行**

```python
# 節數守恆
AddExactlyOne(x[u, *, *])                             for each unit u

# 班級不衝堂
AddAtMostOne(covers(u,s) for u in units_of(class))    for each class, slot

# 教師不衝堂
AddAtMostOne(covers(u,s) for u in units_of(teacher))  for each teacher, slot

# 教室不衝堂
AddAtMostOne(covers_room(u,s,r) for u in units)       for each room, slot
```

三個「不衝堂」在模型裡是**完全同構的**——都是「同一資源在同一 slot 上最多一
次」。這正是把時段編成整數的回報。

不可用時段（班級 blocked、教師 unavailable、連堂不可跨午休）不需要約束，
**直接不建立那些變數**，模型更小也更快。

**軟約束轉成懲罰變數**

```python
# 「老師一天最多 N 節」：over ≥ 當天節數 − N，代價 = over × weight
over = NewIntVar(0, periods)
Add(over >= sum(covers of that teacher on that day) - N)
penalties.append((over, weight))

Minimize(Σ weight × penalty_var)
```

用 `>=` 而非 `==` 是刻意的：目標式在最小化，會自動把 `over` 壓到理論下界，
不需要精確等式，模型更鬆、求解更快。

**候選教室的簡化**

```python
def candidate_rooms(unit):
    if subject.room_type is None:
        return [class.homeroom]        # 原班教室，只有一個選項
    return rooms_of_type(room_type)    # 專科教室才需要選
```

範例學校 328 個單元中，只有約 1/3 需要專科教室、且多半只有一間可選。變數數量
因此從 328×35×17 ≈ 195,000 降到約 12,000。**這是國小場景最大的一個優化**。

### 6.3 人工微調：鎖定 + 局部重排

自動排課永遠不可能一次到位。教務主任一定會想把某堂課挪一格。設計上：

1. 使用者在 UI 拖拉，前端**即時檢查三大衝堂**（純前端規則，不呼叫後端）
2. 滿意的部分按「鎖定」→ 該單元 `pinned_slot` 被設定
3. 按「重排」→ 求解器只在未鎖定的單元上搜尋

`Unit.pinned_slot` 在建立變數時只保留該 slot，所以鎖定是**零成本**的——不需要
額外的約束，只是少建變數，反而更快。這讓「排 80% 自動 + 20% 人工」的實際
工作流程變得順暢。

## 7. 實測結果

原型在 `prototype/`，範例是一所 12 班國小（6 年級 × 2 班，19 位教師，
17 間教室，132 筆配課，328 個待排單元）。

```
$ python3 run.py --time 90 --class 101 --teacher S_PE

可行性檢查：通過

狀態      : OPTIMAL
耗時      : 1.71s
已排時段  : 344
總懲罰成本: 8

未能完全滿足的軟性需求：
  - 體育避開第 5 節（成本 8）

--- 硬約束驗證 ---
班級衝堂：0 件
教師衝堂：0 件
教室衝堂：0 件
節數不符：0 件
排進不上課時段：0 件
```

英語老師甲的「週三不排課」與 101 導師的「週五不排課」都**完整滿足**，唯一的
妥協是有一堂體育排在第 5 節。

**規模測試**（48 班、75 位教師、1312 個單元，約為大型國小的兩倍）：

```
狀態 OPTIMAL　耗時 31.7s　懲罰 96　硬衝突 0 件
```

**無解診斷**（把 102 導師設成「週五不排課」+「一天最多 4 節」，但他有 19 節）：

```
硬約束版本 → 前置檢查即攔下：
  ✗ 教師 102 導師 配課 19 節，但一天最多 4 節 × 4 個可上課日 = 16 節

軟約束版本 → 給出違反最少的課表：
  狀態 OPTIMAL　懲罰 128
  !  102 導師 一天最多 4 節（超出的節數）（成本 120）
  !  體育避開第 5 節（成本 8）
```

軟約束版本完整守住了「週五不排課」（權重 150），只在日上限上超出 3 節——
這正是我們希望權重設計達成的取捨。

## 8. 系統架構建議

```
┌─────────────────────────────────────────────────┐
│  Web 前端                                        │
│   基本資料維護 │ 配課作業 │ 需求蒐集表單          │
│   課表檢視（班級／教師／教室 三視角）             │
│   拖拉微調 + 前端即時衝突檢查                     │
└───────────────────┬─────────────────────────────┘
                    │ REST / JSON
┌───────────────────▼─────────────────────────────┐
│  應用後端（Django / FastAPI / Spring）           │
│   CRUD │ 可行性檢查（同步，毫秒級）              │
│   排課任務派送（非同步）                          │
└───────────────────┬─────────────────────────────┘
                    │ 佇列（Celery / RQ）
┌───────────────────▼─────────────────────────────┐
│  排課引擎 Worker（獨立行程）                      │
│   CP-SAT 求解，回報進度與中途最佳解                │
└─────────────────────────────────────────────────┘
```

幾個實務要點：

- **求解必須非同步。** 幾十秒的 HTTP 請求會被各種東西砍掉。派工作、輪詢進度、
  完成通知。
- **CP-SAT 支援 callback 回報中途解**，可以做「已找到一份課表，還在最佳化中」
  的體驗，讓使用者隨時可以喊停接受。
- **課表版本化。** 每次求解存成一個版本，可以比較、回溯、標記為正式發布。
- **三視角是同一份資料的三種投影**（原型的 `render.py` 就是這樣寫的），
  不要為每個視角各存一份。
- **需求蒐集表單化。** 讓老師自己填「哪幾天不排課」「一天最多幾節」，直接
  產生 `Constraint` 記錄，省掉教務組長謄寫的功夫，也留下誰要求了什麼的紀錄。

## 9. 建議的開發順序

1. 基本資料 CRUD（班級、教師、教室、科目、課綱節數）
2. 配課介面 + **即時可行性檢查**（這一步就能解決學校八成的痛苦，即使還沒自動排課）
3. CP-SAT 引擎，先只做硬約束，確認排得出來
4. 逐條加入軟約束，每加一條就檢查課表品質有沒有變好
5. 三視角檢視 + 匯出（Excel / PDF）
6. 拖拉微調 + 鎖定重排
7. 需求蒐集表單、版本管理、歷史學年度複製

第 2 步的價值常被低估。很多學校真正的痛點不是「排不出來」，而是「排到一半才
發現某位老師被配了 28 節」。
